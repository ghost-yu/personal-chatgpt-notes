### Pile 图的 Raw Size、Epochs 与 Effective Size

`pile.png` 有 22 个来源组件，其中包括网页、论文、代码和论坛。表底 Raw Size 为 **825.18 GiB**，Effective Size 为 **1254.20 GiB**，所以字幕的“825 GB”省略了单位与重复使用口径。以图中 PubMed Central 为例，raw 90.27 GiB、epochs 2.0、effective 约 180.55 GiB；四舍五入可能使直接乘法与显示值略有差异。weight 为 14.40%，而不是 raw/825.18 的占比。

用于理解此表的教学关系为：

$$
E_i\approx R_i e_i,\qquad p_i=\frac{E_i}{\sum_j E_j}.
$$

$R_i$ 是组件原始大小，$e_i$ 是重复采样倍率，$E_i$ 是有效大小，$p_i$ 是混合权重；$i,j$ 遍历组件。两倍重复不意味着磁盘必须再存一份同样数据，也不代表整齐执行整数个 epoch。若不同来源的 token/byte 比例不同，字节权重也不能直接等同于最终 token 权重。这个式子是本讲解释表格的教学表达，不冒充论文编号公式。

这些图是**语料统计表**，不是任务准确率表；它们能支持容量规划与混合分布理解，不能证明某一语料必定提升某个模型的准确率。图片中的下载入口属于历史资源清单，本篇未重新承诺所有地址当前可下载。

## 3. map-style 与 iterable-style：先分清接口【必须会】

map-style 的重点是 `dataset[index]`：给一个索引，返回对应样本。它不规定全部数据必须在 `__init__` 放进 RAM；可以在 `__getitem__` 里读取图片/文本，也可以索引已经建立的 Arrow 表。

iterable-style 的重点是 `iter(dataset)`：返回一个样本流，使用 `next` 或 `for` 消费。常见实现不提供随机索引和可用的 `len`，但“可迭代”不意味着无限，也不自动保证内存小；若实现先 `list(...)` 全部装入内存，接口仍可能是 iterable。

字幕先讲 PyTorch 的 `torch.utils.data.Dataset/IterableDataset`，后面讲 HF 的 `datasets.Dataset/IterableDataset`。这两套库有相同类别名称，但不是同一个类；HF 还有自己的列、features、Arrow 与 streaming 处理逻辑。[PyTorch 接口说明](https://docs.pytorch.org/docs/stable/data.html)

### 教学补充：两个类的最小形式

下面展示 PyTorch 协议的最小形式。实际运行版本见 [数据读取教学补充](代码/数据读取_教学补充.py)：`IndexedRows` 明确接收特征 Tensor；`RangeRows` 额外按 worker 分片。本段简单 `RangeRows` 未处理多 worker，不能直接用于多 worker 消重：

```python
from torch.utils.data import Dataset, IterableDataset

class IndexedRows(Dataset):
    def __init__(self, rows):
        self.rows = rows
    def __len__(self):
        return len(self.rows)
    def __getitem__(self, index):
        return self.rows[index]

class RangeRows(IterableDataset):
    def __init__(self, start, stop):
        self.start, self.stop = start, stop
    def __iter__(self):
        for i in range(self.start, self.stop):
            yield {'value': i}
```

`class X(Base)` 表示继承，`self` 为当前对象。`__init__` 保存状态；`__len__` 支持 `len(obj)`；`__getitem__` 支持方括号索引；`__iter__` 用 `yield` 每次给一条。`range(3,8)` 是 3–7，右边界 8 不包含。字幕中 100 行 5 列例子的“100 个样本”与“5 个特征”应区分，不能把列数当样本数。

`DataLoader` 再负责批次、worker 与 collate；默认 collate 可以把数值组为 tensor，但普通字符串不会自动变成 token ID。DataLoader 的 batch size 与 `.map(batched=True)` 的预处理批次是两种不同配置。

多 worker 的 iterable dataset 若每个 worker 都遍历相同数据源，会产生重复；要按 `get_worker_info()` 或库支持的分片方式分配。多 GPU 训练还需要处理 rank 分片；`streaming=True` 本身不能替代完整分布式采样设计。

## 4. Arrow 与 memory mapping【必须会】

Arrow 是列式数据表示。假设每行有 `text,label`，列式表示将同列值放在对应数组结构里；它不是简单把所有字符串粘成一个没有边界的大字符串。字符串还需要 offsets 等信息，列也可能由多个 chunk/record batch 构成。只读 label 时可以利用列布局，读取完整行时仍要组合所需列。

memory mapping 将文件地址映射进进程的虚拟地址空间。访问某些页面时，由操作系统通过页面机制处理，可能触发磁盘读取与缓存；**映射 20 GB 文件不等于立刻让进程 RSS 增加 20 GB，也不等于永远只占极小内存**。遍历越来越多数据、保留 Python 对象、建立转换缓存、预取和 OS page cache 都会影响实占与峰值。

Datasets 2.19.2 的 `table.py` 中 `MemoryMappedTable.from_file` 调用 Arrow 映射读取辅助函数，底层使用 `pa.memory_map` 和 IPC reader；这是可核对的 mmap 路径。[固定源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/table.py)

教学补充的独立 Arrow 读取：

```python
with pa.memory_map('table.arrow', 'r') as source:
    table = pa.ipc.open_stream(source).read_all()
    rows = table.to_pylist()
```

`with` 为上下文管理器，离开代码块时关闭 source；`open_stream` 解析这里写出的 Arrow IPC stream，不能直接拿来解析任意 JSON 文件。`read_all` 建立 Arrow 表结构，**不等于全部转换成 Python 行对象**；`to_pylist()` 会物化 Python 列表，所以本实验只用 5 行，不推荐对数百 GB 全量调用。

JSONL 原始文本、Arrow 数据字节、Arrow 文件大小和 RSS 是不同量。最新教学补充的 5 行 LF JSONL 为 **215 bytes**、`Dataset.data.nbytes` 为 **145 bytes**、手写 Arrow IPC 文件为 **648 bytes**。旧 [教学验证.json](复现/outputs/教学验证.json) 的 Windows CRLF JSONL 为 220 bytes，5 个换行各多 1 byte，内容行相同但文件字节不同。文件有 schema/元数据开销，绝不能据此认为每个格式永远按固定比例更小。`nbytes` 不是 RSS，更不代表 GPU 显存。

## 5. `load_dataset` 的两条路线【必须会】

以下为本次教学补充；只读自建 JSONL 文件：

```python
from datasets import load_dataset

normal = load_dataset('json', data_files={'train': 'tiny.jsonl'}, split='train')
streamed = load_dataset(
    'json', data_files={'train': 'tiny.jsonl'}, split='train', streaming=True)
```

`load_dataset` 是模块函数。`'json'` 选择通用 JSON loader；`data_files` 指明来源及 split 名；`split='train'` 返回单一数据对象，省略它通常返回 split 字典。`streaming` 默认 False；True 走 iterable 路线。`'json'` 不等于 Hub 上某个叫 json 的语言模型。

普通路线可能先解析文本、生成 Arrow cache，再建立 Dataset；因此第一次准备可能较慢并增加磁盘占用。已经存在的 Arrow cache 与 OS cache 会影响第二次加载耗时。`keep_in_memory`、缓存配置和构造方式也能影响常规 Dataset 是否以内存表保存；`Dataset.from_dict` 不能仅因叫 Dataset 就判定必有 mmap 文件。

streaming 路线按遍历读取来源，可以是本地文件也可以是远程分片；它不先完整建立同样的 Arrow 转换缓存。它仍可能读取头信息、进行文件查询、维护缓冲；不能把对象构造称为绝对“零时间/零 I/O”。源数据若在远程，网络、重试、格式与压缩方式都会影响使用。

固定版本 `load.py` 的 `load_dataset` 在 streaming 分支调用 builder 的 `as_streaming_dataset`；非 streaming 分支进入数据准备，再返回常规 Dataset。[源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/load.py)

## 6. 索引、切片、列与批次的类型【必须会】

对普通 Dataset：

```python
normal[0]             # 一行 dict
normal[1:3]           # 两行，返回 dict-of-lists
normal['text']        # 这一列的 Python 值；大数据不要盲目全量取列
normal.select([3, 1]) # 一个新的 Dataset，按指定行顺序
```

本次 `normal[1:3]` 实际返回：

```python
{'id': [1, 2], 'text': ['中文文本', 'a b c'], 'label': [1, 0]}
```

`[1:3]` 不返回 Dataset，也不是 `list[dict]`。`select` 返回 Dataset。访问转成 Python 字符串/列表时会产生 Python 对象，不能泛称每一种索引都是零拷贝。某些版本可用的 API 也会变化；本篇观察固定于 2.19.2。

| 位置 | 类型/shape | 下一步 |
|---|---|---|
| JSONL 每行 | 一份 JSON 对象 | parser 读取 |
| `normal[0]` | `dict`：text 为 `str`，label 为 int | 单样本转换 |
| `.map` 单样本参数 | 同样是 `dict` | 返回新增/覆盖列 |
| `.map(batched=True)` 参数 | `dict[str,list]`，各列长度 $B$ | 批量 tokenizer |
| tokenizer 输出 IDs | 通常 `list[list[int]]`，变长 | collator padding |
| padding 后 | `[B,S]` 的 IDs/mask | 下游 embedding `[B,S,d]` |

这里的 $B$ 是预处理批次大小，$S$ 为 padding 后 token 长度，$d$ 为模型隐藏维。本次真实 GPT-2 分词使用 5 条文本，变长 IDs 经 padding 得到 CPU `torch.int64[5,7]`；mask 同形，按 mask 去掉 padding 后 decode 恢复全部文本。原 GPT-2 无 pad token，补充明确执行 `tokenizer.pad_token = tokenizer.eos_token` 修改 tokenizer 状态；这里复用已有 EOS，不增加词表。没有加载 embedding 或语言模型，`[B,S,d]` 是后续接口说明。

## 7. `.map()`：处理时间何时发生？【必须会】

`.map` 与 memory map 的区别，可以用副作用计数直接观察。教学代码：

```python
seen = []
def add_chars(row):
    seen.append(row['id'])
    return {'chars': len(row['text'])}

mapped = normal.map(add_chars, load_from_cache_file=False)
```

`add_chars` 为普通函数，接受一行 dict，返回新字段；原字段默认保留。`normal.map` 返回新 Dataset，原 normal 的列不因此增加。本次为避免命中已有结果缓存，使用 `load_from_cache_file=False`；5 行全部处理完成后方法才返回，`seen=[0,1,2,3,4]`。补充对同一个 `cache_file_name` 再执行 `load_from_cache_file=True`，新增回调次数为 0，结果一致。这是显式文件缓存复用，不能用固定文件名保证更改函数后的缓存一定有效。若复用 map cache，不能把“函数没有调用”误判为 iterable 延迟。

对流式数据：

```python
lazy = streamed.map(add_chars)
first = next(iter(lazy))
```

`IterableDataset.map` 返回新的可迭代处理管线，定义时未执行转换；`next(iter(lazy))` 才读取并转换所需样本。本次单样本 map 定义后计数为 0，取首条后为 1；另建迭代器再取前两条，计数序列变为 `[0,0,1]`，说明再次遍历可重新执行转换，而非复用第一次的全量结果。

内部 `iterable_dataset.py` 用 `MappedExamplesIterable` 包装来源与变换，迭代期间执行；常规 `Dataset.map` 则管理转换、缓存、写入与返回结果。[固定源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/iterable_dataset.py)

字幕里的 tokenization 语义可写成以下参考模板，非原保存代码。实际补充使用同一接口和固定 GPT-2 tokenizer，但为了观察调用，用 `batch_size=2`，而不是模板的 32：

```python
tokenized = streamed.map(
    lambda batch: tokenizer(batch['text'], truncation=True),
    batched=True, batch_size=32)
```

`lambda` 是简短匿名函数；`batch['text']` 为 `list[str]`；tokenizer 常返回 IDs 与 attention_mask 等列。流式 batched map 取一条输出，也可能先读取/转换一个完整预处理 batch，因此不能把“读取 1 条输出”一律等同于“只处理 1 条输入”。

实际流式 tokenizer map 定义时调用数为 0；取 1 条输出处理了输入 id `[0,1]`。重新遍历 5 条又处理 `[0,1]`、`[2,3]`、`[4]`，所以总调用记录为 `[[0,1],[0,1],[2,3],[4]]`。最后 1 条是不满的 batch，也正常处理；分词后仍返回 Python list，另一次 `padding=True, return_tensors='pt'` 才得到整齐 Tensor。

`batched=True` 不意味着自动 padding、固定 tensor 或 GPU 推理。通常保持一个 batch 返回各列长度一致；若分块改变行数，旧列必须移除或同步变换，例如 `remove_columns=...`，否则可能产生字段长度冲突。字符长度函数 `len(str)` 数的是 Python 字符，不是 UTF-8 byte 数，也不是 token 数。

## 8. `take`、`skip` 与 shuffle【必须会】

```python
first_five = list(streamed.take(5))
after_1000 = streamed.skip(1000)
one = next(iter(after_1000))
```

HF 的 `take(n)` 与 `skip(n)` 返回新的 IterableDataset 视图，`list(...)` 才实际消费。take 为最多前 n 条，样本不足时可少于 n 条；skip 从原顺序跳过 n 条后给剩余所有行，不是“只取后面 n 条”。若按零起始，skip(1000) 后首条是索引 1000，也就是人类计数第 1001 条。

对顺序 JSONL 流，skip 通常仍需迭代并跳过前面记录，不能当数据库索引或 O(1) 文件 seek。本次固定版本真实计数：`stream.map(fn).skip(3)` 取首条时转换了 `[0,1,2,3]`；`stream.skip(3).map(fn)` 只转换了 `[3]`。两者首条 id 都是 3，但前者对被跳过样本也做转换。这类 API 不建立对任意行的随机索引。`len(streamed)` 本次实际抛出 `TypeError`；不能写依赖已知总行数的常规 for-range 循环。

另一个常见误解是 streaming shuffle 等同于全数据精确随机排列。普通 Dataset 可以生成全局索引排列；IterableDataset 常用 buffer shuffle，buffer_size 限制可暂存的样本数，并可打乱分片顺序，通常是近似混洗。设 seed 有助于重现同一配置，但文件顺序、分片、epoch、worker/rank 的变化也会影响结果。[官方比较](https://huggingface.co/docs/datasets/v2.19.0/about_mapstyle_vs_iterable)

本实验用 `buffer_size=3, seed=42`，5 行得到 `[0,2,1,3,4]`，重跑配置顺序相同且没有缺失/重复行；这仅验证小例子的覆盖与确定性，不证明混洗统计上等价于全局均匀排列。

## 9. 测内存和吞吐，如何避免错算【建议会】

字幕提到约 19.54 GB 数据、两次遍历共 141 秒、进程约 1 GB。这些历史观察没有原测速源码、完整环境和原数据，不能当本次结果，更不能称为磁盘带宽实测。

若每轮遍历等效处理 $D$ 个字节，共 $k$ 轮、总耗时 $T$ 秒，则平均每轮耗时 $\bar t=T/k$，应用层有效吞吐为：

$$
v_{\text{app}}=\frac{kD}{T}=\frac{D}{\bar t}.
$$

以 $D=19.54$、$k=2$、$T=141$ 计算，约为 0.277 个同口径容量单位/秒，而 $19.54/141\approx0.139$ 少算了一轮。GB 与 GiB 必须统一；当 $D$ 来自 Arrow `nbytes` 而不是实际设备读取量时，该数只能叫按数据大小估计的应用层吞吐。

第二轮可能命中 OS page cache；JSON parser、Python 对象构造、切片、tokenizer 和 I/O 都可能进入计时。要测设备带宽，需要明确冷/热缓存、读取字节数、访问模式与工具。单看 `psutil.Process().memory_info().rss` 是一个时间点的进程实占，包含 Python/库等开销，不是“只有 dataset 的内存”，也不是系统所有 page cache。峰值应另行采集，GPU 显存与这些 CPU 指标分开。

streaming 同样不是资源免费：它以重复解析/联网、有限随机访问、近似 shuffle 等代价避免完整物化。mmap 的随机访问与 prepared cache 更适合某些重复训练；streaming 的按需访问适合只扫有限样本或来源超出本地磁盘容量的场景。
