**语料（corpus）**是一批用于训练或研究的文本，网页、文章、代码都可以作为文档。数据流程再把它们切成样本。语言模型预训练从文本中学习预测后续内容，本讲先看这些文本从哪里来、怎样读取。

第09讲的token是分词器切出的文本单位，token ID是查词表得到的整数。**一行、一文档、一字符、一byte、一token不是同一个计数。** byte是存储单位，1 byte=8 bit；字符可能需要多个UTF-8 bytes，token数又取决于分词器。

## 2. 直接读C4原表：305 GB究竟是什么【必须会】

![C4原论文Table1：三个版本的规模及统计口径](图片/C4原论文_Table1_三个版本.png)

出处：[Documenting Large Webtext Corpora: A Case Study on the Colossal Clean Crawled Corpus](https://aclanthology.org/2021.emnlp-main.98.pdf)，EMNLP2021，PDF第2页/印刷页1287 Table1。C4最早由T5工作提出，这张表来自后续语料研究。

从左往右读：Dataset是版本名，documents是文档数，tokens是分词后单位数，size是文件容量。表注说明：一个document是单个URL抓到的文本；token用SpaCy English tokenizer计数；size是压缩JSON文件大小。million是百万，billion是十亿，trillion是万亿。

C4.EN一行给出3.65亿文档、1560亿SpaCy token和305GB压缩文件。文档数、token计数与压缩容量分别描述不同统计对象；改用GPT-2等分词器时，token数需要重新计算。

## 3. Pile原表：磁盘上的一份数据，可以被读多次【建议会】

![Pile原论文Table1：原始大小、采样倍率与有效大小](图片/Pile原论文_Table1_语料组成.png)

出处：[The Pile，arXiv:2101.00027v1，PDF第3页Table1](https://arxiv.org/pdf/2101.00027v1)。表列出划分held-out前的22个组件；held-out是留作验证或测试的部分。

PubMed Central原始大小90.27GiB，Epochs=2.0表示在完整混合语料的一轮中约使用两遍，Effective Size约180.55GiB，Weight为最终混合数据的14.40%。显示数值经过舍入，因此90.27×2与180.55略有差别。

最右列Mean Document Size是每份文档的平均大小，KiB=1024 bytes。带†的来源表示从已有工作取用、只做最少预处理；这些符号不是模型评分。

用更小的自建例子手算：A有10个容量单位、读2次；B有20个、读1次。有效大小分别为20、20，总共40，A权重是20/40=50%，不是原始10/30。一般写作：

$$E_i\approx R_i e_i,\qquad p_i=E_i/\sum_jE_j.$$

i表示来源，R_i为原始大小，e_i为重复倍率，E_i为有效大小，p_i为字节权重；分母汇总所有来源的有效大小。重复采样可以通过读取实现。各来源token/byte比例不同，若要算token权重，还需分词后统计。

底行825.18GiB和1254.20GiB分别为原始大小与有效大小。GiB按2的30次方字节计，GB按10的9次方字节计。比较容量时，应统一单位、压缩方式和重复次数。

## 4. 磁盘、内存、缓存，先各放在自己的位置【必须会】

**磁盘文件**在SSD/硬盘上长期保存；**RAM内存**放进程正在使用的对象和缓冲；**GPU显存**是另一种资源，读一个数据文件不会自动把它放进显存。**缓存（cache）**保存可复用结果：HF准备好的Arrow文件可能是磁盘缓存，操作系统也会在内存中缓存读过的文件页，这两种缓存不同。

JSON用文本表示字段和值，JSONL每行保存一个完整JSON对象，适合逐行解析。下面建立6行数据，id为行编号、text为文本；小列表方便逐条核对，正式大语料则可直接从文件逐行提供记录。

`Path`管理路径，`TemporaryDirectory`建立临时目录；`with`让文件/目录在退出代码块时关闭或清理。`def`定义函数，`yield`使函数成为生成器，每次请求下一条才继续执行；`iter`取得迭代器，`next`消费下一项，`list`会消费剩余全部项。`json.dumps`将字典变文本，`json.loads`反向解析。列表推导式 `[row["id"] for row in ...]`逐项提取编号。

```python
import json
from pathlib import Path
from tempfile import TemporaryDirectory

rows = [
    {"id": 0, "text": "cat"}, {"id": 1, "text": "中文"},
    {"id": 2, "text": "a b"}, {"id": 3, "text": "hello"},
    {"id": 4, "text": "x"}, {"id": 5, "text": "end"},
]

def iter_jsonl(path):
    with path.open(encoding="utf-8") as source:
        for line in source:
            yield json.loads(line)

with TemporaryDirectory() as folder:
    file = Path(folder) / "tiny.jsonl"
    with file.open("w", encoding="utf-8", newline="\n") as target:
        for row in rows:
            target.write(json.dumps(row, ensure_ascii=False) + "\n")
    jsonl_bytes = file.stat().st_size
    cursor = iter_jsonl(file)
    first = next(cursor)
    second = next(cursor)
    remaining_ids = [row["id"] for row in cursor]
    replay_ids = [row["id"] for row in iter_jsonl(file)]
    print("前两行:", first, second)
    print("剩余/重新开始:", remaining_ids, replay_ids)
    print("JSONL文件字节数:", jsonl_bytes)
```

同一游标消费0、1后，再迭代得到2–5；重新打开文件则从0开始。`ensure_ascii=False` 保留中文，`newline="
"` 固定LF。`list(cursor)` 会把剩余行收进列表；按需next则一次返回一行。底层文件系统还会管理自己的缓冲。

## 5. 同一文件，HF Datasets的两种读取路线【必须会】

`load_dataset` 是Datasets库的函数：json选择解析器，data_files指定文件，split=train选择数据分组。下面固定用datasets2.19.2和pyarrow16.1.0观察接口。

普通路线解析JSONL、准备Arrow磁盘缓存，返回可按索引访问的Dataset。流式路线返回IterableDataset，按iter/next读取。map-style描述索引接口，streaming描述消费方式，两者的内存使用还取决于缓存和转换。

接着新增chars字段，记录Python字符数。“中文”有2个字符、6个UTF-8字节。普通map通常先执行转换，再返回结果，也可复用缓存；流式map先建立管线，消费样本时执行。用调用计数可以直接看到时机。

```python
import gc
from datasets import load_dataset

with TemporaryDirectory() as folder:
    file = Path(folder) / "tiny.jsonl"
    file.write_text("".join(json.dumps(row, ensure_ascii=False) + "\n" for row in rows),
                    encoding="utf-8", newline="\n")
    normal = load_dataset("json", data_files=str(file), split="train",
                          cache_dir=str(Path(folder) / "cache"))
    streamed = load_dataset("json", data_files=str(file), split="train", streaming=True)
    normal_type = type(normal).__name__
    storage_type = type(normal.data).__name__
    selected_row = normal[3]
    slice_rows = normal[1:3]
    print("对象/存储:", normal_type, storage_type, type(streamed).__name__)
    print("按索引/切片:", selected_row, slice_rows)

    eager_seen = []
    def eager_chars(row):
        eager_seen.append(row["id"])
        return {"chars": len(row["text"])}
    mapped = normal.map(eager_chars, load_from_cache_file=False, keep_in_memory=True)
    original_columns = normal.column_names
    mapped_columns = mapped.column_names
    print("普通map返回时已处理:", eager_seen)

    lazy_seen = []
    def lazy_chars(row):
        lazy_seen.append(row["id"])
        return {"chars": len(row["text"])}
    lazy = streamed.map(lazy_chars)
    before_next = list(lazy_seen)
    iterator = iter(lazy)
    first_lazy = next(iterator)
    iterator.close()
    first_two = list(streamed.take(2))
    after_two = list(streamed.skip(2).take(2))
    print("流式map定义/取一条后:", before_next, lazy_seen, first_lazy)
    print("take2 / skip2再take2:", [r["id"] for r in first_two], [r["id"] for r in after_two])
    # Windows上先释放映射/迭代器，再清理教学临时文件。
    del iterator, lazy, streamed, mapped, normal
    gc.collect()
```

`.append`在列表末尾记编号，函数返回的字典为结果增加字段；`type(...).__name__`读取类型名称。`.map`是数据对象的方法，接收一个函数、返回新数据对象；它不同于Python内置map。这里 `load_from_cache_file=False`不复用已有转换结果，`keep_in_memory=True`将本次小转换结果留在RAM，便于实验结束清理；这不是建议对大数据全量这样设置。原normal仍只有id/text两列，新mapped增加chars。

本轮实际结果：普通对象为Dataset、存储为MemoryMappedTable，流式对象为IterableDataset。`normal[3]`返回 `{'id':3,'text':'hello'}`；`normal[1:3]`返回列到列表的字典 `{'id':[1,2],'text':['中文','a b']}`，并不是新的Dataset。普通map在返回时已经处理 `[0,1,2,3,4,5]`；流式map定义后为 `[]`，取首条后才为 `[0]`。`take(2)`得到0/1，`skip(2).take(2)`得到2/3。skip2是跳过前2条，不是只保留最后2条；顺序文本流通常仍需越过前面的记录。

`iterator.close()` 提前关闭生成器，del释放变量引用，gc.collect()回收不可达对象。这里在退出临时目录前释放Windows文件映射句柄。

## 6. memory mapping怎样让文件“按地址访问”【必须会】

**Arrow**是列式数据表示：id列与text列有各自的数组/缓冲结构，字符串还需要记录边界。它不是“把所有JSON原文拼在一起”。**memory mapping（内存映射）**把文件区域映射进进程的虚拟地址空间，访问相应页面时由操作系统处理实际读入与缓存。虚拟地址像一份可访问的地址范围，不等于同样大小的RAM已全部常驻。

对同样6行数据，`pa.Table.from_pylist` 构造Arrow表，`pa.ipc.new_stream` 写成IPC stream文件，`pa.memory_map(...,"r")` 建立只读映射。`read_all()` 读取表结构并引用缓冲，`to_pylist()` 将行物化成Python字典。大数据读取时可按需要取列或批次。

```python
import pyarrow as pa

with TemporaryDirectory() as folder:
    arrow_file = Path(folder) / "tiny.arrow"
    table = pa.Table.from_pylist(rows)
    with pa.OSFile(str(arrow_file), "wb") as sink:
        with pa.ipc.new_stream(sink, table.schema) as writer:
            writer.write_table(table)
    arrow_file_bytes = arrow_file.stat().st_size
    with pa.memory_map(str(arrow_file), "r") as source:
        mapped_file_type = type(source).__name__
        mapped_table = pa.ipc.open_stream(source).read_all()
        table_nbytes = mapped_table.nbytes
        chinese_text = mapped_table.column("text")[1].as_py()
        restored_rows = mapped_table.to_pylist()
        del mapped_table
    print("映射类型、行1文本:", mapped_file_type, chinese_text)
    print("JSONL/Arrow文件/Arrow数据bytes:", jsonl_bytes, arrow_file_bytes, table_nbytes)
    print("恢复全部6行一致:", restored_rows == rows)
```

映射对象为MemoryMappedFile，6行内容可恢复。JSONL文件153bytes，Arrow文件496bytes，Arrow数据nbytes为93：前两者是文件大小，后者是数据缓冲统计，包含的格式与元数据开销不同。进程驻留内存则要另外测量。

把三个容易混淆的map放在一起：

| 名称 | 它解决什么 | 本页例子 |
|---|---|---|
| map-style接口 | 给索引找样本 | `normal[3]` |
| memory mapping | 文件怎样映射到可访问地址 | `pa.memory_map` |
| 数据集 `.map(fn)` | 给每个样本/批次做转换 | 增加chars字段 |

三种map可以组合使用。实现参照Datasets2.19.2的[table.py](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/table.py)、[load.py](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/load.py)和[iterable_dataset.py](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/iterable_dataset.py)。

## 7. 后面怎样接分词、批次与模型【必须会】

当前JSON行是 `dict`，text为str。做分词时可以调用 `streamed.map(fn, batched=True, batch_size=32)`，fn接收列到列表的字典，`batch['text']`是最多32个字符串，tokenizer返回变长的 `list[list[int]]`。batched表示一次处理多行，不自动补齐长度、不自动搬进GPU。

B条编号补到长度S后，形成整数 `[B,S]`；同形状attention_mask标记真实文本，embedding再查成浮点 `[B,S,d]`，d为隐藏宽度。实际GPT-2分词与padding的例子在下方历史记录中。

流式batched map取一个输出时，可能已经处理整批输入。它的batch_size控制预处理，而DataLoader的batch_size控制训练组批。多worker读取同一流时，要通过分片避免重复读取。

## 8. 内存和吞吐怎样统计【建议会】

映射一个20GB文件不等于RAM立即增加20GB，也不意味着永远只占很少内存。读过的数据页、Python转换结果、预取、操作系统缓存都影响实占和峰值。**RSS**是某时刻进程驻留内存的一种统计，既含库和Python对象，也不能概括系统所有文件缓存。

普通路线首次准备Arrow缓存与随后复用缓存，代价不同；流式路线每次重新遍历可能重做解析/转换。流式shuffle常用有限buffer近似混洗，不等同于把全数据精确均匀打乱。buffer_size限制暂存样本，seed固定只能帮助同配置重放，不替代文件顺序和worker分片管理。

等效每轮处理D字节，k轮用T秒，应用层有效吞吐为kD/T。例如10MB读两轮、用4秒，得到5MB/s。字幕中19.54容量单位、两轮141秒，对应约0.277同口径单位/秒；其中还包含缓存、解析等影响。

`pile.png` 有 22 个来源组件，其中包括网页、论文、代码和论坛。表底 Raw Size 为 **825.18 GiB**，Effective Size 为 **1254.20 GiB**，所以字幕的“825 GB”省略了单位与重复使用口径。以图中 PubMed Central 为例，raw 90.27 GiB、epochs 2.0、effective 约 180.55 GiB；四舍五入可能使直接乘法与显示值略有差异。weight 为 14.40%，而不是 raw/825.18 的占比。

用于理解此表的教学关系为：

$$
E_i\approx R_i e_i,\qquad p_i=\frac{E_i}{\sum_j E_j}.
$$

$R_i$ 是组件原始大小，$e_i$ 是重复采样倍率，$E_i$ 是有效大小，$p_i$ 是混合权重；$i,j$ 遍历组件。两倍重复不意味着磁盘必须再存一份同样数据，也不代表整齐执行整数个 epoch。若不同来源的 token/byte 比例不同，字节权重也不能直接等同于最终 token 权重。这个式子是本讲解释表格的教学表达，不冒充论文编号公式。

这些图是**语料统计表**，不是任务准确率表；它们能支持容量规划与混合分布理解，不能证明某一语料必定提升某个模型的准确率。图片中的下载入口属于历史资源清单，本篇未重新承诺所有地址当前可下载。

## 3. map-style 与 iterable-style：先分清接口【必须会】

map-style 的重点是 `dataset[index]`：给一个索引，返回对应样本。它不规定全部数据必须在 `__init__` 放进 RAM；可以在 `__getitem__` 里读取图片/文本，也可以索引已经建立的 Arrow 表。

iterable-style 的重点是 `iter(dataset)`：返回一个样本流，使用 `next` 或 `for` 消费。常见实现不提供随机索引和可用的 `len`，但“可迭代”不意味着无限，也不自动保证内存小；若实现先 `list(...)` 全部装入内存，接口仍可能是 iterable。

字幕先讲 PyTorch 的 `torch.utils.data.Dataset/IterableDataset`，后面讲 HF 的 `datasets.Dataset/IterableDataset`。这两套库有相同类别名称，但不是同一个类；HF 还有自己的列、features、Arrow 与 streaming 处理逻辑。[PyTorch 接口说明](https://docs.pytorch.org/docs/stable/data.html)

### 教学补充：两个类的最小形式

下面展示 PyTorch 协议的最小形式。实际运行版本见 [数据读取教学补充](代码/数据读取_教学补充.py)：`IndexedRows` 明确接收特征 Tensor；`RangeRows` 额外按 worker 分片。本段简单 `RangeRows` 未处理多 worker，不能直接用于多 worker 消重：

```python
from torch.utils.data import Dataset, IterableDataset

class IndexedRows(Dataset):
    def __init__(self, rows):
        self.rows = rows
    def __len__(self):
        return len(self.rows)
    def __getitem__(self, index):
        return self.rows[index]

class RangeRows(IterableDataset):
    def __init__(self, start, stop):
        self.start, self.stop = start, stop
    def __iter__(self):
        for i in range(self.start, self.stop):
            yield {'value': i}
```

`class X(Base)` 表示继承，`self` 为当前对象。`__init__` 保存状态；`__len__` 支持 `len(obj)`；`__getitem__` 支持方括号索引；`__iter__` 用 `yield` 每次给一条。`range(3,8)` 是 3–7，右边界 8 不包含。字幕中 100 行 5 列例子的“100 个样本”与“5 个特征”应区分，不能把列数当样本数。

`DataLoader` 再负责批次、worker 与 collate；默认 collate 可以把数值组为 tensor，但普通字符串不会自动变成 token ID。DataLoader 的 batch size 与 `.map(batched=True)` 的预处理批次是两种不同配置。

多 worker 的 iterable dataset 若每个 worker 都遍历相同数据源，会产生重复；要按 `get_worker_info()` 或库支持的分片方式分配。多 GPU 训练还需要处理 rank 分片；`streaming=True` 本身不能替代完整分布式采样设计。

## 4. Arrow 与 memory mapping【必须会】

Arrow 是列式数据表示。假设每行有 `text,label`，列式表示将同列值放在对应数组结构里；它不是简单把所有字符串粘成一个没有边界的大字符串。字符串还需要 offsets 等信息，列也可能由多个 chunk/record batch 构成。只读 label 时可以利用列布局，读取完整行时仍要组合所需列。

memory mapping 将文件地址映射进进程的虚拟地址空间。访问某些页面时，由操作系统通过页面机制处理，可能触发磁盘读取与缓存；**映射 20 GB 文件不等于立刻让进程 RSS 增加 20 GB，也不等于永远只占极小内存**。遍历越来越多数据、保留 Python 对象、建立转换缓存、预取和 OS page cache 都会影响实占与峰值。

Datasets 2.19.2 的 `table.py` 中 `MemoryMappedTable.from_file` 调用 Arrow 映射读取辅助函数，底层使用 `pa.memory_map` 和 IPC reader；这是可核对的 mmap 路径。[固定源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/table.py)

教学补充的独立 Arrow 读取：

```python
with pa.memory_map('table.arrow', 'r') as source:
    table = pa.ipc.open_stream(source).read_all()
    rows = table.to_pylist()
```

`with` 为上下文管理器，离开代码块时关闭 source；`open_stream` 解析这里写出的 Arrow IPC stream，不能直接拿来解析任意 JSON 文件。`read_all` 建立 Arrow 表结构，**不等于全部转换成 Python 行对象**；`to_pylist()` 会物化 Python 列表，所以本实验只用 5 行，不推荐对数百 GB 全量调用。

JSONL 原始文本、Arrow 数据字节、Arrow 文件大小和 RSS 是不同量。最新教学补充的 5 行 LF JSONL 为 **215 bytes**、`Dataset.data.nbytes` 为 **145 bytes**、手写 Arrow IPC 文件为 **648 bytes**。旧 [教学验证.json](复现/outputs/教学验证.json) 的 Windows CRLF JSONL 为 220 bytes，5 个换行各多 1 byte，内容行相同但文件字节不同。文件有 schema/元数据开销，绝不能据此认为每个格式永远按固定比例更小。`nbytes` 不是 RSS，更不代表 GPU 显存。

## 5. `load_dataset` 的两条路线【必须会】

以下为本次教学补充；只读自建 JSONL 文件：

```python
from datasets import load_dataset

normal = load_dataset('json', data_files={'train': 'tiny.jsonl'}, split='train')
streamed = load_dataset(
    'json', data_files={'train': 'tiny.jsonl'}, split='train', streaming=True)
```

`load_dataset` 是模块函数。`'json'` 选择通用 JSON loader；`data_files` 指明来源及 split 名；`split='train'` 返回单一数据对象，省略它通常返回 split 字典。`streaming` 默认 False；True 走 iterable 路线。`'json'` 不等于 Hub 上某个叫 json 的语言模型。

普通路线可能先解析文本、生成 Arrow cache，再建立 Dataset；因此第一次准备可能较慢并增加磁盘占用。已经存在的 Arrow cache 与 OS cache 会影响第二次加载耗时。`keep_in_memory`、缓存配置和构造方式也能影响常规 Dataset 是否以内存表保存；`Dataset.from_dict` 不能仅因叫 Dataset 就判定必有 mmap 文件。

streaming 路线按遍历读取来源，可以是本地文件也可以是远程分片；它不先完整建立同样的 Arrow 转换缓存。它仍可能读取头信息、进行文件查询、维护缓冲；不能把对象构造称为绝对“零时间/零 I/O”。源数据若在远程，网络、重试、格式与压缩方式都会影响使用。

固定版本 `load.py` 的 `load_dataset` 在 streaming 分支调用 builder 的 `as_streaming_dataset`；非 streaming 分支进入数据准备，再返回常规 Dataset。[源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/load.py)

## 6. 索引、切片、列与批次的类型【必须会】

对普通 Dataset：

```python
normal[0]             # 一行 dict
normal[1:3]           # 两行，返回 dict-of-lists
normal['text']        # 这一列的 Python 值；大数据不要盲目全量取列
normal.select([3, 1]) # 一个新的 Dataset，按指定行顺序
```

本次 `normal[1:3]` 实际返回：

```python
{'id': [1, 2], 'text': ['中文文本', 'a b c'], 'label': [1, 0]}
```

`[1:3]` 不返回 Dataset，也不是 `list[dict]`。`select` 返回 Dataset。访问转成 Python 字符串/列表时会产生 Python 对象，不能泛称每一种索引都是零拷贝。某些版本可用的 API 也会变化；本篇观察固定于 2.19.2。

| 位置 | 类型/shape | 下一步 |
|---|---|---|
| JSONL 每行 | 一份 JSON 对象 | parser 读取 |
| `normal[0]` | `dict`：text 为 `str`，label 为 int | 单样本转换 |
| `.map` 单样本参数 | 同样是 `dict` | 返回新增/覆盖列 |
| `.map(batched=True)` 参数 | `dict[str,list]`，各列长度 $B$ | 批量 tokenizer |
| tokenizer 输出 IDs | 通常 `list[list[int]]`，变长 | collator padding |
| padding 后 | `[B,S]` 的 IDs/mask | 下游 embedding `[B,S,d]` |

这里的 $B$ 是预处理批次大小，$S$ 为 padding 后 token 长度，$d$ 为模型隐藏维。本次真实 GPT-2 分词使用 5 条文本，变长 IDs 经 padding 得到 CPU `torch.int64[5,7]`；mask 同形，按 mask 去掉 padding 后 decode 恢复全部文本。原 GPT-2 无 pad token，补充明确执行 `tokenizer.pad_token = tokenizer.eos_token` 修改 tokenizer 状态；这里复用已有 EOS，不增加词表。没有加载 embedding 或语言模型，`[B,S,d]` 是后续接口说明。

## 7. `.map()`：处理时间何时发生？【必须会】

`.map` 与 memory map 的区别，可以用副作用计数直接观察。教学代码：

```python
seen = []
def add_chars(row):
    seen.append(row['id'])
    return {'chars': len(row['text'])}

mapped = normal.map(add_chars, load_from_cache_file=False)
```

`add_chars` 为普通函数，接受一行 dict，返回新字段；原字段默认保留。`normal.map` 返回新 Dataset，原 normal 的列不因此增加。本次为避免命中已有结果缓存，使用 `load_from_cache_file=False`；5 行全部处理完成后方法才返回，`seen=[0,1,2,3,4]`。补充对同一个 `cache_file_name` 再执行 `load_from_cache_file=True`，新增回调次数为 0，结果一致。这是显式文件缓存复用，不能用固定文件名保证更改函数后的缓存一定有效。若复用 map cache，不能把“函数没有调用”误判为 iterable 延迟。

对流式数据：

```python
lazy = streamed.map(add_chars)
first = next(iter(lazy))
```

`IterableDataset.map` 返回新的可迭代处理管线，定义时未执行转换；`next(iter(lazy))` 才读取并转换所需样本。本次单样本 map 定义后计数为 0，取首条后为 1；另建迭代器再取前两条，计数序列变为 `[0,0,1]`，说明再次遍历可重新执行转换，而非复用第一次的全量结果。

内部 `iterable_dataset.py` 用 `MappedExamplesIterable` 包装来源与变换，迭代期间执行；常规 `Dataset.map` 则管理转换、缓存、写入与返回结果。[固定源码](https://github.com/huggingface/datasets/blob/2.19.2/src/datasets/iterable_dataset.py)

字幕里的 tokenization 语义可写成以下参考模板，非原保存代码。实际补充使用同一接口和固定 GPT-2 tokenizer，但为了观察调用，用 `batch_size=2`，而不是模板的 32：

```python
tokenized = streamed.map(
    lambda batch: tokenizer(batch['text'], truncation=True),
    batched=True, batch_size=32)
```

`lambda` 是简短匿名函数；`batch['text']` 为 `list[str]`；tokenizer 常返回 IDs 与 attention_mask 等列。流式 batched map 取一条输出，也可能先读取/转换一个完整预处理 batch，因此不能把“读取 1 条输出”一律等同于“只处理 1 条输入”。

实际流式 tokenizer map 定义时调用数为 0；取 1 条输出处理了输入 id `[0,1]`。重新遍历 5 条又处理 `[0,1]`、`[2,3]`、`[4]`，所以总调用记录为 `[[0,1],[0,1],[2,3],[4]]`。最后 1 条是不满的 batch，也正常处理；分词后仍返回 Python list，另一次 `padding=True, return_tensors='pt'` 才得到整齐 Tensor。

`batched=True` 不意味着自动 padding、固定 tensor 或 GPU 推理。通常保持一个 batch 返回各列长度一致；若分块改变行数，旧列必须移除或同步变换，例如 `remove_columns=...`，否则可能产生字段长度冲突。字符长度函数 `len(str)` 数的是 Python 字符，不是 UTF-8 byte 数，也不是 token 数。

## 8. `take`、`skip` 与 shuffle【必须会】

```python
first_five = list(streamed.take(5))
after_1000 = streamed.skip(1000)
one = next(iter(after_1000))
```

HF 的 `take(n)` 与 `skip(n)` 返回新的 IterableDataset 视图，`list(...)` 才实际消费。take 为最多前 n 条，样本不足时可少于 n 条；skip 从原顺序跳过 n 条后给剩余所有行，不是“只取后面 n 条”。若按零起始，skip(1000) 后首条是索引 1000，也就是人类计数第 1001 条。

对顺序 JSONL 流，skip 通常仍需迭代并跳过前面记录，不能当数据库索引或 O(1) 文件 seek。本次固定版本真实计数：`stream.map(fn).skip(3)` 取首条时转换了 `[0,1,2,3]`；`stream.skip(3).map(fn)` 只转换了 `[3]`。两者首条 id 都是 3，但前者对被跳过样本也做转换。这类 API 不建立对任意行的随机索引。`len(streamed)` 本次实际抛出 `TypeError`；不能写依赖已知总行数的常规 for-range 循环。

另一个常见误解是 streaming shuffle 等同于全数据精确随机排列。普通 Dataset 可以生成全局索引排列；IterableDataset 常用 buffer shuffle，buffer_size 限制可暂存的样本数，并可打乱分片顺序，通常是近似混洗。设 seed 有助于重现同一配置，但文件顺序、分片、epoch、worker/rank 的变化也会影响结果。[官方比较](https://huggingface.co/docs/datasets/v2.19.0/about_mapstyle_vs_iterable)

本实验用 `buffer_size=3, seed=42`，5 行得到 `[0,2,1,3,4]`，重跑配置顺序相同且没有缺失/重复行；这仅验证小例子的覆盖与确定性，不证明混洗统计上等价于全局均匀排列。

## 9. 测内存和吞吐，如何避免错算【建议会】

字幕提到约 19.54 GB 数据、两次遍历共 141 秒、进程约 1 GB。这些历史观察没有原测速源码、完整环境和原数据，不能当本次结果，更不能称为磁盘带宽实测。

若每轮遍历等效处理 $D$ 个字节，共 $k$ 轮、总耗时 $T$ 秒，则平均每轮耗时 $\bar t=T/k$，应用层有效吞吐为：

$$
v_{\text{app}}=\frac{kD}{T}=\frac{D}{\bar t}.
$$

以 $D=19.54$、$k=2$、$T=141$ 计算，约为 0.277 个同口径容量单位/秒，而 $19.54/141\approx0.139$ 少算了一轮。GB 与 GiB 必须统一；当 $D$ 来自 Arrow `nbytes` 而不是实际设备读取量时，该数只能叫按数据大小估计的应用层吞吐。

第二轮可能命中 OS page cache；JSON parser、Python 对象构造、切片、tokenizer 和 I/O 都可能进入计时。要测设备带宽，需要明确冷/热缓存、读取字节数、访问模式与工具。单看 `psutil.Process().memory_info().rss` 是一个时间点的进程实占，包含 Python/库等开销，不是“只有 dataset 的内存”，也不是系统所有 page cache。峰值应另行采集，GPU 显存与这些 CPU 指标分开。

streaming 同样不是资源免费：它以重复解析/联网、有限随机访问、近似 shuffle 等代价避免完整物化。mmap 的随机访问与 prepared cache 更适合某些重复训练；streaming 的按需访问适合只扫有限样本或来源超出本地磁盘容量的场景。

### 教学补充的调用链与 API

`verify_delivery.py → run_demo(temp_folder, tokenizer_dir)`，后者返回可 JSON 保存的普通 dict，含实测记录，不返回模型或 Dataset 对象。临时 JSONL、Arrow cache、IPC、保存目录在实验结束清理；Windows 下提前关闭短读迭代器，避免仍打开的文件句柄阻止清理。worker 类放在可正常 import 的模块内，验证入口有 `if __name__ == '__main__'`，避免 Windows spawn 重复执行主流程。

| 补充 `run_demo` 函数 | folder/tokenizer_dir：Path，无默认值 | 返回结果 dict；写临时数据，修改本地 tokenizer 的 pad 设置，不改原 notebook |
