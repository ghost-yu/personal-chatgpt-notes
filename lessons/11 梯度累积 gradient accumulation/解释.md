# 第 11 讲：梯度累积 gradient accumulation

梯度累积让模型按小批次计算、按较大的有效批次更新参数。它省下的主要是同时存在的激活及其计算图，模型参数、参数梯度与优化器状态不会因为累积 4 次就缩小到四分之一。实现关键在于：每个 micro-batch 反向传播，但在一个累积窗口结束时才更新参数和清零梯度。

## 2. 为什么累积后相当于更大的有效 batch【必须会】

先固定一组参数 $\theta$，一个窗口有 $K$ 个等大小 micro-batch，每批 $b$ 个样本。设第 $k$ 批第 $j$ 个样本损失为 $\ell_{k,j}(\theta)$，该批平均 loss 为：

$$
L_k(\theta)=\frac1b\sum_{j=1}^{b}\ell_{k,j}(\theta),
\qquad L_{\mathrm{window}}(\theta)=\frac1K\sum_{k=1}^{K}L_k(\theta).
$$

微分对求和具有线性性：

$$
\nabla_\theta L_{\mathrm{window}}=
\sum_{k=1}^{K}\nabla_\theta\left(\frac{L_k}{K}\right).
$$

$\theta$ 是全部模型参数向量，$b$ 是物理小批次样本数，$K$ 是累积次数，$k,j$ 分别索引小批次与样本。上式是本讲教学推导，不冒充某篇论文的编号公式。对每个 $L_k/K$ backward 并保留 `.grad` 的和，就得到合并 $Kb$ 个样本平均 loss 的梯度；窗口内必须不执行参数更新，才能让这些梯度都在同一个 $\theta$ 上计算。

数值例子：线性模型 $\hat y=wx+c$，MSE 为样本平方误差的平均。取 $w=1,c=0$，输入 `x=[1,2,3,4]`，标签全 0。单样本对 $w$ 的梯度是 `[2,8,18,32]`，对 $c$ 是 `[2,4,6,8]`；累积平均得到 `[15,5]`，与一次 batch=4 完全相同。若学习率 0.1，更新后 `[w,c]=[-0.5,-0.5]`。

早期精确有理数与中心差分独立核对平方损失导数；最新又用真实 PyTorch float64 Linear/SGD 执行两段原 Markdown 循环。合并与完整累积梯度均为 `[15,5]`，更新后均为 `[-.5,-.5]`。若每个样本都立刻更新，后续样本在不同参数上求梯度，结果为 `[0.2112,-0.4992]`，不会等于一次窗口更新。

## 3. 有效 batch 与等价条件【必须会】

对等权重、等大小、完整窗口的数据并行设置：

$$
B_{\mathrm{effective}}=b_{\mathrm{per\ device}}\times K\times D.
$$

$D$ 为参加数据并行、各自持有不同样本的设备/进程数。模型分片到两卡不自动等于 $D=2$；GPU 数量与数据并行样本数必须依据运行方式判断。原 baseline `b=4,K=1` 与累积 `b=1,K=4` 在同一 $D$ 下有效 batch 相等。

这种梯度关系也有边界：

- 不等大小 micro-batch，需要按实际样本数加权。
- 变长语言模型 loss 若按有效 token 平均，需要按有效 token 数归一化。
- BatchNorm、跨样本对比损失等依赖同批样本，拆开 forward 可能改变目标。
- Dropout 的随机掩码、浮点求和次序等可能造成数值差异，不能保证完整训练逐位相同。
- 梯度裁剪、optimizer/scheduler 更新应在合适窗口边界；每个小批次裁剪再相加不等于合并后裁剪。

“小 batch 一定不稳定、精度更低”是过强说法。梯度噪声与 batch 有关系，但最终收敛与泛化还依赖学习率、样本、优化器和总更新数；累积是控制有效 batch 的方法，不是普遍提高准确率的保证。

## 4. 普通 loop 与累积 loop 的关键行【必须会】

单元 5 和 7 均是 **Markdown 中的代码块**，不是 notebook 自动执行单元；其中的 `model`、`criterion`、`optimizer`、`data_loader` 与 `device` 都没有在该块定义，是框架示意。

普通 loop 对每批执行：

```python
preds = model(inputs)
loss = criterion(preds, labels)
loss.backward()
optimizer.step()
optimizer.zero_grad()
```

`model(inputs)` 调用 PyTorch 模型的 forward 路径；criterion 通常为 loss 对象；loss 为标量。`backward()` 求导并累加到叶子参数的 `.grad`；`step()` 利用已有梯度更新参数；`zero_grad()` 清掉上一窗口残留。`.to(device)` 将 inputs/labels 移到指定设备，不会自动改变模型或 tokenizer。

原累积块的核心：

```python
gradient_accumulation_steps = 4
for batch_idx, (inputs, labels) in enumerate(data_loader):
    inputs = inputs.to(device)
    labels = labels.to(device)
    with torch.set_grad_enabled(True):
        preds = model(inputs)
        loss = criterion(preds, labels)
        loss /= gradient_accumulation_steps
        loss.backward()
        if ((batch_idx + 1) % gradient_accumulation_steps == 0) or \
           ((batch_idx + 1) == len(data_loader)):
            optimizer.step()
            optimizer.zero_grad()
```

`enumerate` 产生从 0 开始的批次索引及数据；因此用 `batch_idx+1` 转为第几批。`%4==0` 每 4 批触发更新；最后一批的条件避免遗留梯度未 step。`with` 是上下文管理器，`set_grad_enabled(True)` 在块中开启 autograd；它不替代 `model.train()`，后者还影响 dropout/BatchNorm。

`loss /=4` 是缩放损失，因此缩放反向传播贡献；实际工程常写 `loss = loss /4`，保留未缩放 loss 另用于日志。一个窗口内不 zero_grad，缓冲自然累加；循环开始前还应明确 `optimizer.zero_grad(...)`，尤其 notebook 重跑可能有旧梯度。

| 变量/调用 | 类型与 shape | 状态变化 |
|---|---|---|
| `inputs` | 依模型而定；BERT ID 为 int64 `[b,S]` | 移设备 |
| `labels` | BERT 分类为 int64 `[b]` | 移设备 |
| `preds/logits` | 分类浮点 `[b,2]` | 构建当前 micro 图 |
| `loss` | 浮点标量 `[]` | 除窗口归一化因子 |
| 参数 `p` | 例如权重 `[out,in]` | step 前保持不变 |
| `p.grad` | 与对应参数同 shape | 每次 backward 相加，窗口结束清除 |

## 5. 末尾不足窗口与不等 batch【必须会】

假设 `K=4`，某 epoch 有 10 个 micro-batch。原条件的更新边界为第 `[4,8,10]` 批；最后一个窗口只有 2 批，却仍各自除以 4。若两批等大小，其梯度是该两批平均梯度的 **1/2**。原代码包含了“最后 step”，但没有因此完成正确的窗口归一化。

上述平方损失的前两个样本，实际窗口平均梯度为 `[5,3]`，原除以 4 得 `[2.5,1.5]`。若总批数刚好整除 K，这个问题不出现；原 1024 样本的设置就属于容易整除的示例。

如果第 $k$ 批有 $n_k$ 个样本，即便窗口完整，简单 average-of-means 也可能错误。正确样本平均为：

$$
L_{\mathrm{window}}=
\frac{\sum_k n_k L_k}{\sum_k n_k}.
$$

例子：小批次为 `x=[1,2]` 和 `x=[10]`，标签全 0，在 `w=1,c=0` 上各批梯度 `[5,3]` 与 `[200,20]`。等权平均得到 `[102.5,11.5]`，但按 2:1 加权或合并三样本，正确为 `[70,26/3]`。

### 教学补充：单机序列分类的正确样本归一化

下面是分类模型模板，使用 `CrossEntropyLoss(reduction='sum')` 对整个窗口实际样本数归一化，处理尾批与不等 batch。该分类模板没有单独执行；同一窗口算法已在 [可执行教学补充](代码/窗口归一化_教学补充.py)中用每样本一个输出的 Linear/MSE/SGD 真实验证，不把不同 loss 实现混称为同一运行：

```python
from itertools import islice
criterion_sum = torch.nn.CrossEntropyLoss(reduction='sum')
model.train()
iterator = iter(data_loader)
while True:
    window = list(islice(iterator, gradient_accumulation_steps))
    if not window:
        break
    total_samples = sum(labels.shape[0] for _, labels in window)
    optimizer.zero_grad(set_to_none=True)
    for inputs, labels in window:
        inputs, labels = inputs.to(device), labels.to(device)
        logits = model(inputs).logits
        loss = criterion_sum(logits, labels) / total_samples
        loss.backward()
    optimizer.step()
```

这里 `window` 暂存输入批次，理想情况下仍在 CPU；不是同时保存 K 个 GPU forward 图。每个 micro forward 后立即 backward，才继续下一批。`islice` 最多取 K 项；短窗口自动处理；`sum` 计算当前窗口实际样本数。如果 data_loader 已直接提供 GPU tensor，则暂存窗口也有 GPU 内存代价；这个简单模板不是所有生产场景的最优读法。

补充 `train_weighted_windows(model,batches,steps=4,learning_rate=.1)` 返回每个窗口的更新边界、样本数与更新前真实梯度。模型为 CPU float64 Linear(1,1)，输入/目标 `[n,1]`，MSE sum 除总样本数；最后只有2样本时梯度 `[5,3]`、SGD参数 `[.5,-.3]`，原除4循环参数 `[.75,-.15]`。2+1不等批次真实梯度约 `[70,8.6667]`；10个micro窗口为4/8/10。这个补充没有修改原循环、原 notebook 或历史输出。

LLM 的 token-level loss 要进一步替换分母。Causal LM 内部通常先 shift labels，再忽略 `-100`；有效 token 数应依据真正进入 loss 的目标位置计算，不能一律用 `labels.numel()` 或样本条数。框架可能已经完成 loss 缩放，手动再除 K 会重复缩放。

## 6. `x.grad` 累加与 `retain_graph`【必须会】

单元 8–10：

```python
x = torch.tensor(1., requires_grad=True)
y = x**2
y.backward(retain_graph=True)
x.grad
y.backward()
x.grad
```

`x` 是浮点标量、shape `[]`；`requires_grad=True` 请求追踪导数；`x` 为叶子张量。`y=x**2` 的导数为 $2x=2$，第一遍 `.grad=2`；没清零再对同一个 y backward，贡献再加 2，成为 4。

`retain_graph=True` 保留这一次 forward 的计算图，使同一个 y 可再次 backward；它不是字幕中的“retain grade”，也不是从图中 detach。一般梯度累积对每个 micro-batch 重新 forward，有新图，**不需要 retain_graph=True**；只保留参数梯度，不保留所有历史计算图。错误保留 K 个完整图可能抵消节省激活的目标。

真实执行原/注释单元8–10均得到 float32标量梯度2→4。独立补充再对已释放的同一图第三次backward，实际捕获RuntimeError；随后设 `x.grad=None` 并新建 `x**2` 图反向，重新得到2。

`zero_grad(set_to_none=True)` 将梯度设为 None，与写入全零张量有部分行为差异；下一次 backward 会创建/填充梯度。普通训练中不要拿 `.data` 绕开 autograd，也不要把 tensor loss 的引用无限加入列表；日志保存 `loss.detach().item()` 更适合。

## 8. Trainer 参数及历史源码调用链【建议会】

单元 23 为 baseline；单元 26 重复数据、模型与工具定义，改成：

```python
training_args = TrainingArguments(
    per_device_train_batch_size=1,
    gradient_accumulation_steps=4,
    **default_args)
trainer = Trainer(model=model, args=training_args, train_dataset=ds)
result = trainer.train()
```

`**default_args` 将字典展开为命名参数；`output_dir='tmp'` 为产物目录；`num_train_epochs=1` 为一遍数据；`report_to='none'` 关闭默认外部报告集成；`log_level='error'` 只改变日志显示。`evaluation_strategy='steps'` 设了按步评估，却没有 eval_dataset；若达到实际评估触发步数，可能报缺评估数据，应改为不评估或提供 eval_dataset。原短运行可能没达到默认评估间隔，所以不能直接断言原程序必定在开头失败。

Trainer v4.30.0 主链为：准备 DataLoader/optimizer/scheduler → 内部训练 loop → `training_step` → `compute_loss` → backward → 更新边界进行 clip/optimizer/scheduler/zero_grad。`training_step` 对多 GPU loss 做 mean；非专门 AMP/Apex 分支调用 `self.accelerator.backward(loss)`。函数末尾 `loss.detach()/K` 返回的是**日志值**，不能把这行单独当作实际梯度归一化的证据。[源码](https://github.com/huggingface/transformers/blob/v4.30.0/src/transformers/trainer.py)

辅助 Accelerate v0.20.1 的 `Accelerator.backward` 在普通路径中先 `loss / self.gradient_accumulation_steps` 再 backward。DeepSpeed 等路径有专门处理，不能截一行代替整条框架逻辑。[辅助源码](https://github.com/huggingface/accelerate/blob/v0.20.1/src/accelerate/accelerator.py)

该历史 Trainer 的更新边界也不是原 Markdown 手写末批条件的直接复制，包含 `total_batched_samples % K`、短 epoch 特判与 Accelerate 状态；框架不同版本对非完整窗口的处理可能改变。这里没有运行框架末批路径，不声称所有版本已经按我们希望的样本/token 数正确加权。

AMP 混合精度与累积可组合：一个窗口内维持一致的 scale，先完成累积，再 unscale、clip、step/update。DDP 通信可用恰当的 `no_sync` 减少前几个 micro-batch 的同步，但要遵守框架边界；这些不是把 `optimizer.step` 机械挪位置就能全部解决。

### 最新实测版本的归一化路径

本次 [Trainer4.44.2.training_step](https://github.com/huggingface/transformers/blob/v4.44.2/src/transformers/trainer.py) 同样调用 `self.accelerator.backward(loss)`；[Accelerate0.34.2.backward](https://github.com/huggingface/accelerate/blob/v0.34.2/src/accelerate/accelerator.py) 的普通非DeepSpeed路径先除K再调用真正 backward。其末尾 detach/K 仍是日志返回值。实测完整窗口用真实 Trainer/AdamW/线性scheduler；回调只观察事件、forward hook只保存shape/dtype，不替换loss或更新实现。没有执行框架末尾不足窗口、AMP/DDP分支，不能从这次完整窗口对照推出它们全部正确。

| 实际对象/方法 | 输入与默认值参照 | 返回与状态变化 |
|---|---|---|
| `Tensor.backward` | 标量y，gradient默认None，retain_graph默认依create_graph（本例False） | 返回None；叶子.grad累加，默认释放图中保存量 |
| optimizer `zero_grad` | torch2.5.1 set_to_none默认True | 返回None；清梯度，不更新参数/Adam状态 |
| optimizer `step` | 本例SGD lr=.1，Trainer默认AdamW lr=5e-5 | 根据grad更新参数及优化器状态；按窗口触发 |
| HF `Dataset.from_dict` | 各列具有同样N行的dict | 新Dataset；`set_format('pt')`另行原地修改取出格式 |
| `TrainingArguments` | baseline batch4/K默认1；累积batch1/K4；epoch1；默认seed42 | 配置对象，不做forward；steps评估仍需实际eval_dataset |
| `Trainer.train` | 保存的model/args/train_dataset；无resume参数 | TrainOutput；实际改变参数/optimizer/scheduler/global_step |
| `print_summary` 普通函数 | result为TrainOutput，无默认值 | 返回None；打印metrics与NVML时点值，不重新训练 |

## 9. 读原历史结果：显存节省伴随速度代价【建议会】

原单元 24、27 的数字写在 Markdown 中，属于历史记录：

| 设置 | runtime 秒 | samples/s | GPU memory 标为 MB |
|---|---:|---:|---:|
| per-device batch 4、K=1 | 38.0194 | 26.934 | 21296 |
| per-device batch 1、K=4 | 102.8176 | 9.959 | 13166 |

根据这些数字重算：占用少 8130 MiB，约下降 38.18%；时间为原来的 2.70 倍，吞吐下降约 63.02%。不是“四倍累积就四倍省内存”，也不是字幕某段错念的“3G”。历史训练 loss 为约 0.7216 与 0.7096；随机数据与标签不同、无验证集，不能据此评估准确率提升。

`print_gpu_utilization()` 调用 NVML 获取各卡 `info.used`，最后把它们相加，再 `//1024**2` 输出。这个单位实际是 MiB，打印文本写 MB；它是设备总占用，可包含其他进程与驱动开销，不等于当前训练进程 tensor 内存。测量在训练后进行，**不是峰值采集**；还可能受 allocator 缓存和之前 notebook 对象残留影响。本次真实NVML见1张物理卡，但CPU torch的 `cuda.device_count()` 为0，原函数循环0次打印0MB；单独查询NVML记录非零used字节。因此这个0不能解释为GPU不存在或空闲。

字幕明确说使用双卡；历史 steps/s×runtime 约为 128 次更新，也与单 epoch 1024 样本、有效 batch 8 相容。但缺少完整启动命令、驱动、框架版本，不能仅靠 `.to('cuda')` 推出确切的数据并行方式。4090 的互联条件不足以单独解释全部 2.70 倍差距；小 batch 降低硬件利用率、增加 forward/backward 次数与调度开销，也可能影响速度。

图 `grad-accumulation.png` 的三个蓝色 batch 箭头汇入一个绿色 Weight update，表达“多个计算贡献 → 一次参数更新”；没有新增训练参数，也不表示保留三个计算图同时 backward。图用三个 batch，伪代码 K=4，是示意数量差异，不是额外算法。
